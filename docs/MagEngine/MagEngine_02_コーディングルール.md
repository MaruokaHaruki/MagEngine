# MagEngine コーディングルール

## 適用範囲と優先順位

自作コード、テスト、設定、仕様変更に適用する。externals/ の規約は変更しない。

ユーザーの明示指示 → 既存コード・設計・周辺規約 → この規約 → 一般的なベストプラクティスの順で判断する。既存コードに合わせた例外は、実際に判断が必要な場合だけ理由を履歴へ残す。

## 言語・命名・整形

- C++20を基準とする。現行vcxprojの設定に合わせ、依頼なく言語バージョンを変えない。
- 新規の独立したコードは、変数 camelCase、関数・型 PascalCase、メンバ name_、定数 kPascalCase を基本とする。
- 既存クラスの規約を優先し、同一クラス内に別の命名規約を持ち込まない。
- インデント、波括弧、ポインタの空白は同じファイルに合わせる。一括整形や改名をしない。
- include、using、ライブラリ依存は必要最小限にする。数行の処理のために依存を増やさない。

## 責務と変更範囲

- 内部整備では、目的を達成するために必要なクラス・処理の書き直しを認める。短い差分だけを優先せず、部分修正と書き直しのどちらが責務・寿命・可読性を明確にするかで判断する。
- 書き直す前に対象範囲、維持する挙動、変更する契約、移行する呼び出し元、回帰確認を仕様へ記録する。依頼範囲内の書き直しは認めるが、無関係な再設計・新機能追加へ広げない。
- 書き直したコードにも本書のコメント・区切り線・配置規則を適用する。既存の検証・エラー処理を落とさず、実装・呼び出し元・テスト・設定を揃えて移行する。
- 改修前に共有処理と全呼び出し元を調べ、原因を共通箇所で直す。
- 既存API・ヘルパー・Contextを使う。用途のないラッパー、抽象クラス、設定項目を追加しない。
- ヘッダーには利用側が必要な契約を書き、実装詳細はcppへ置く。ただし自明な短い関数を不要に分割しない。
- 仕様・調査の依頼でコードを実装しない。既存の未コミット変更を上書き・取り消ししない。

## エラーと入力境界

| 対象 | 必須の扱い |
| --- | --- |
| ファイル、JSON、WAV、モデル | 読み込み結果、サイズ、要素数、形式、境界を実行時に検証する |
| HRESULT等の外部API失敗 | 失敗を確認し、無効なリソースを使う前に呼び出し経路を止める |
| 容量不足・不正な公開API引数 | Releaseでも範囲外参照・無効ハンドル操作へ進めない |
| 内部の不変条件 | assertを使用できる。ただし副作用や必須処理をassert内に書かない |
| キャッシュ | 成功後に登録する。検索だけの処理でoperator[]を使って欠損エントリを作らない |

既存APIが例外を使う箇所では例外、結果型を返す箇所では結果型を優先する。今回のために全体共通のエラー基盤は作らない。エラーには資産名・操作・理由を含め、握りつぶして成功扱いにしない。

## 所有権・寿命・GPU

- 単独所有にはunique_ptr、COMには既存のComPtrを使う。shared_ptrは共有所有が実際に必要な場合に限る。
- 保持する生ポインタ／参照には所有者・寿命・nullptr可否を明示する。非所有参照を勝手に解放しない。
- 非同期APIへ渡すメモリは完了まで保持する。ローカル配列やvectorのdata()を寿命外まで参照させない。
- GPUが参照するリソースはFence完了前に解放・再利用・上書きしない。Descriptorにも同じ制約を適用する。
- GPU構造体の型・サイズ・アラインメントはHLSLと合わせ、必要なstatic_assertで直接確認する。
- スレッド安全性を根拠なく保証しない。スレッドをまたぐ場合は実際の共有状態と同期範囲を仕様に書く。

## 時間・性能

- 経過時間の単位は秒とし、可変フレーム更新には検証済みdeltaTimeを渡す。
- gameplayDeltaTimeとunscaledDeltaTimeを用途で選び、ポーズ・スロー中の進行を仕様にする。
- 1つの共有システムをエミッターごとに重複更新しない。更新回数と責任者を明確にする。
- 毎フレームの不要な文字列生成、コンテナコピー、確保を避ける。計測なしの複雑な最適化は行わない。
- 描画順や容量制限を変える場合は、見た目と欠落時の挙動も確認する。

## コメント

コメント詳細は既存の `docs/COMMENT_RULES_FOR_CODEX.md` を参照する。Obsidianにある同名資料は既存資料として残す。ユーザーの明示指示と周辺の形式を優先する。

- 原則日本語。公開APIは既存の `/// @brief`、必要に応じ `@param`、`@return`、`@note`、`@warning` を使う。
- 理由、前提、単位、所有権、順序、失敗時の挙動を書く。コードの逐語説明は増やさない。
- NOTE、TODO、FIXME、WARNING、HACKは大文字で統一し、理由・影響・解除条件を必要に応じて付ける。対応済みのものは削除する。
- 区切り線は周辺形式を継続し、数行ごとに増やさない。既存の `///====` を別形式へ一括変換しない。
- 既知の制約を残す暫定処理は `// shortcut: 制約、変更すべき条件` の形で記録する。安全性の欠落をこのコメントで正当化しない。

## コメント・区切り線・配置の必須ルール

2026-11-05のユーザー指示により、新規コードと書き直したコードで遵守する。既存のObject3d.cpp、PlayerMovementComponent.h等の形式を基準とし、既存ファイルへの部分修正では周囲の形式を保つ。以下の役割分担を、装飾の一括置換ではなく構造の基準として使う。

| 形式 | 役割 | 配置 |
| --- | --- | --- |
| ファイルヘッダー | ファイルの役割 | 主要な新規・書き直しファイルの先頭 |
| `///=============================================================================` | namespace・クラス・cpp関数等の大きな境界 | 対象の直前。次行に日本語の短い見出し |
| `///--------------------------------------------------------------` | 大分類の中の責務群 | ヘッダーの初期化・操作・描画登録・取得・設定・内部状態等の直前 |
| `//========================================` | 関数内やデータ群の処理ブロック | 準備・検証・反映等、責務が切り替わる箇所 |
| Doxygenコメント | API・型の契約 | 宣言直前 |
| `// NOTE:` 等 | 局所的な判断理由・制約 | 対象処理の直前 |

### ファイルと宣言

- ファイルヘッダーには `\file` と役割が分かる `\brief` を書く。作者・日付を推測で追加しない。
- 公開APIは概要を記述し、必要に応じて引数、単位、戻り値、nullptr可否、失敗、順序、所有権を補足する。自明な事項を埋めるためだけにタグを増やさない。
- 新しい独立ファイルは `/// @brief` 形式を基本とする。既存ファイルで `/**----` と `\brief` のブロック形式を使っている場合は、それを継続する。同じAPI群で形式を混在させない。
- 保持する非所有ポインタには、所有者と有効な期間を記述する。時間・角度・距離の単位、配列上限、GPU構造体の対応も、誤用のおそれがある箇所で明示する。

```cpp
/*********************************************************************
 * \file   ExampleController.h
 * \brief  規約を示すための宣言例
 *********************************************************************/
#pragma once

///=============================================================================
/// コントローラ
class ExampleController {
public:
	///--------------------------------------------------------------
	/// 初期化・更新
	/// @brief 初期状態へ戻す
	void Initialize();

	/// @brief 経過時間を進める
	/// @param deltaTime 経過時間（秒）。0以上の有限値を渡す。
	void Update(float deltaTime);

private:
	///--------------------------------------------------------------
	/// 内部状態
	float elapsedTime_ = 0.0f; // 初期化後の経過時間（秒）
};
```

### 関数と処理ブロック

- cppの主要関数には大きな区切りと見出しを置く。ヘッダー内の短いgetter等へ関数ごとの大きな区切りを重ねない。
- ブロック見出しは「入力検証」「GPU転送の準備」等、そのまとまりの役割を示す。見出しのために処理を細分化しない。
- コードから分かる1行ごとの動作説明は不要。ただし、処理を探すための分類見出しは残す。
- 区切り線は対象と同じインデントに揃える。新規の独立ファイルはタブインデント・開始波括弧を同じ行・ポインタの `Type *name` を基本とし、部分修正では周辺を優先する。
- 見出しを揃えるための大量の空白・タブや、変更と無関係な行末コメントの列揃えを増やさない。

```cpp
///=============================================================================
/// 設定の反映
// NOTE: 読み込み失敗時に現在の設定を維持するため、検証後に置き換える。
// 以下は関数内の配置例であり、実装コードではない。
//========================================
// 入力検証

//========================================
// 検証済み設定の反映
```

### クラス内の並び

新規・書き直しクラスは「初期化・終了・更新 → 主要操作 → 描画登録や外部連携 → 状態取得 → 設定変更 → private内部処理 → メンバ変数」の順を基本とする。存在しない分類の見出しは作らない。所有権や呼び出し順を読み取れるまとまりを優先する。

### 実装時の確認

1. 変更箇所でコメント・区切り線の形式が周囲と揃っているか。
2. 見出しと実際の責務が一致し、分類の粒度が過剰でないか。
3. 所有権・寿命・単位・更新順・失敗時の説明が実装と一致しているか。
4. 書き直しによって既存の注意事項や検証が失われていないか。
5. 仕様・履歴へ変更理由と実際の検証結果を残したか。

自動フォーマットだけで遵守を保証したとせず、変更したコードをこの基準でレビューする。

## テストとレビュー

- 原因を直接検出する回帰テストを追加する。正常系、境界、異常系から必要なものを選ぶ。
- 実装をテスト側へコピーしない。getterや代入だけを確認する低価値テストは追加しない。
- assertだけのテストはReleaseで消えるため、テストの判定は終了コードへ反映する既存方式を使う。
- 独立したTestプロジェクトを新設しない。既存の検証ソースは保持し、必要な検証方法は変更内容に応じて選ぶ。テスト容易性だけのために大きな公開APIを増やさない。
- Debug／Releaseのビルドと対象CPUテストを基本とする。GPUリソースの変更ではDebug Layer、シーン遷移、終了処理も確認する。
- レビューでは正確性、寿命、境界、状態遷移を優先する。好みの違いを重大な問題として扱わない。

## 変更の完了条件

仕様IDに対応する実装・呼び出し元・fixture・設定が揃い、必要な確認を実施し、仕様と履歴が実態に一致していること。未確認が残る場合は「実装済み・検証待ち」とし、成功扱いにしない。

現行ソリューションはMagEngineとGameの2プロジェクトに限定する。Minimal・Core・Test・ImGui用の独立プロジェクトを追加しない。ビルドと層境界の確認例：

```powershell
msbuild MagEngine.sln /m /p:Configuration=Debug /p:Platform=x64
& .\scripts\VerifyEngineBoundary.ps1
```

Releaseは構成名をReleaseに変える。以前のCPUテスト実行結果は履歴として残すが、削除したTestプロジェクトのコマンドを現行手順として記載しない。ビルド・実行・ユーザーによる動作確認・Hosted CIの結果は分けて報告する。
